# Development continuity instructions — Goakit

## Scope and sources

- Read `docs/decisions/` (ADRs), `docs/product.md`, `docs/architecture.md`, `docs/decisions.md`, and `docs/delivery.md` before changing functionality. Where an older document contradicts an accepted ADR, the ADR wins.
- This fork is Thales Reiser's own product, and Thales makes all decisions ([ADR 0001](docs/decisions/0001-fork-as-independent-product.md), [ADR 0004](docs/decisions/0004-roles-single-owner.md)). Thales's current explicit instructions define the delivery and take precedence over technical proposals.
- Gabriel Guerguen's brief (linked in `docs/product.md`), Paper screens, and comments are the product reference. They inform the product; they do not limit the fork's scope.
- The Paper screens and the first implementation scope are in `docs/implementation.md`. Consult that material before expanding the UI. Do not invent a visual identity or new flows; the old setup screen was not an approved product design.
- Scope: a pnpm/Turborepo monorepo with the API at the core. `apps/api` (NestJS with the Fastify adapter, REST `/v1`, [ADR 0002](docs/decisions/0002-backend-typescript-nestjs.md)); `apps/mobile` (the current Expo app, local-first with SQLite); `apps/web` (Next.js App Router for public list pages with Open Graph previews, account and account deletion, and the back office, [ADR 0003](docs/decisions/0003-web-app-nextjs.md)); `packages/domain` (pure TypeScript rules shared by the app and the API, running offline on the phone); `packages/contracts` (OpenAPI generated by the API and the generated TypeScript client); `packages/db-schema` (Drizzle); `packages/tokens`; `packages/config`.
- The monorepo foundation exists (EST-01.2): pnpm workspaces (`pnpm-workspace.yaml`) and Turborepo (`turbo.json`), with the Expo app in `apps/mobile` (`@goakit/mobile`, mock data and in-memory state) and the shared TypeScript, ESLint, and Prettier configuration in `packages/config` (`@goakit/config`, EST-01.3). `apps/api`, `apps/web`, and the other `packages/*` are planned and not built yet. Do not describe planned parts as existing, and add backend, persistence, authentication, public links, or integrations only through the plan task that introduces them.
- Suggestion ("intelligence") features are pluggable providers in the API. Every suggestion reaches the user as an adaptation with a reason, which the user accepts or rejects.

## Stack and organization

- Expo + React Native + strict TypeScript + Gluestack UI. NativeWind is the existing styling engine; do not mix it with UniWind.
- Check `apps/mobile/package.json`, `pnpm-lock.yaml`, and `.nvmrc`. Use documentation matching the installed versions, including [Expo SDK 57](https://docs.expo.dev/versions/v57.0.0/) and [Gluestack v5](https://v5.gluestack.io/ui/docs/home/getting-started/installation). NativeWind is in preview; do not automatically apply v4 recipes.
- Expo Router is a proposal, not an installed dependency. Do not migrate the entry point without recording the decision.
- Consult `apps/mobile/components/ui/` before creating components. Keep screens/logic organized by feature, mock data centralized in `apps/mobile/src/mocks/` when needed, and types in `apps/mobile/src/types/`.
- Do not put the entire application in `App.tsx`. Do not create abstractions or empty folders ahead of the task that needs them.
- Domain rules are pure functions without UI, networking, or storage, so they can move to `packages/domain` once it exists (planned).
- Existing color tokens are in `apps/mobile/global.css`; do not duplicate their values in components. The initial Paper scale is in `apps/mobile/src/theme/patterns.ts` and `docs/implementation.md`. Prefer semantic roles and reusable variants.

## Invariants

- Completion is one boolean per item. Progress is personal and derived; do not implement separate purchase/prepare/pack stages.
- Copies and reused lists have their own identities and independent objects. Do not propagate changes between an original and a copy.
- Adaptations are proposals with reasons; only accepted proposals change the new list. Preserve personal choices. This applies to every suggestion provider.
- Never share the entire personal object. Generate an explicit projection containing only allowed fields, without progress or private items. The server enforces the same projection; the UI filter is never the only guarantee.
- Creating and using lists does not require an account. Identification is required only to publish a link.
- Privacy defaults and exception precedence remain open. Do not decide them implicitly through defaults.
- Never present simulations as real: mock feedback must not look like a real account, link, synchronization, or publication. Do not request real passwords in simulated flows.
- Current types are preliminary presentation types, not final API/database contracts. Contracts will come from the API's OpenAPI document (`packages/contracts`, planned).

## Agent operating guide

- **Worktree and branch**: work in your own git worktree. Create the branch from `origin/main`, named `type/ID-description` (for example `docs/EST-07.3-adrs-agent-guide`). Do not touch other worktrees or the main clone.
- **Remotes**: push and open pull requests only to `thalesreiser/goakit`, always with `--repo thalesreiser/goakit`. Never push or open pull requests to the upstream repository (`gabrielguerguen/goakit`).
- **Nothing runs locally**: no installs, builds, tests, type checks, or servers. CI on the pull request is the verification. Read CI results and fix failures in the same pull request.
- **Scope of a pull request**: one task per pull request. Dependency additions, removals, and upgrades go in their own pull request.
- **Stop and ask Thales** before acting on: design, UI, or UX; breaking changes to the API contract or data model; privacy rules; security; infrastructure or anything with a cost; major dependency upgrades. Present 2–3 options with a recommendation.
- **Decide routine implementation choices yourself** and list them under an "Implementation choices" heading in the pull request body.
- **Language and format**: commits, branches, and pull requests in English, using Conventional Commits.
- **No AI attribution**: no AI attribution or mentions in commits, pull requests, code, or documentation (no co-author trailers, no generated-by footers).
- **Merging**: agents never merge. Thales reviews and merges.
- **Trello**: the main session updates the Trello board; agents do not.

## Verification and delivery

- Verification happens in CI (`.github/workflows/ci.yml`: type checks, tests, lint, Expo dependency check, and bundle export). Do not claim a check passed unless CI shows it.
- Documentation: check consistency, references, and decisions.
- UI/navigation/dependency changes: rely on the CI compatibility and bundle checks; record which devices were tested, if any. Do not claim mobile testing just because export passed.
- When implementing rules, test relevant behavior (privacy, copy independence, applying adaptations once, empty lists). Avoid redundant documentation/type tests.
- Keep credentials out of Git. Use branches and pull requests for review.
- Document what works, what is simulated, and what remains open. Do not announce planned flows as completed.

## Documentation language

Maintain repository documentation in English. The application interface and mock content remain in Portuguese (pt-BR) unless Thales explicitly requests a product-language change. Preserve exact UI labels when they help someone find a control while testing.
